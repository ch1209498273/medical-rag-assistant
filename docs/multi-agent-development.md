# 多 Agent 开发

这里的“多 Agent”描述开发协作方式，不描述产品请求期间的运行时结构。当前 v1.0 产品运行时仍是一个 FastAPI 应用内的单一 RAG 编排：同一个请求依次经过清理、检索、重排、生成、引用核验和持久化，不会在运行时启动或路由到开发 Agent。

## 开发角色

| 角色 | 负责什么 | 交付物/检查点 |
| --- | --- | --- |
| 主 Agent | 维护范围、依赖顺序、用户确认点、风险和最终整合 | 规格、任务 brief、基线、合并决定 |
| 实现 Agent | 按已批准的单一任务边界修改代码、测试或文档 | 最小实现、RED/GREEN 证据、文件清单 |
| 测试 Agent | 独立运行聚焦测试、回归、构建和接口检查 | 失败原因、通过计数、可复现命令 |
| 安全 Agent | 检查 Key、真实资料、路径、链接、导出和历史边界 | 安全扫描、阻断项、修复或明确残余风险 |
| 文档 Agent | 将实际代码和报告整理为 README、架构、评测和案例 | 可读叙事、相对链接、限制和决策记录 |

角色可以由不同执行回合承担，也可以在小任务中由同一协作者承担；角色名不是产品权限，也不是运行时服务名。项目负责人参与业务范围、方案选择、资料授权、指标判断和回滚决策，Agent 辅助实现、验证和整理，不把 Agent 产出冒充为完全手写。

## 任务交接流程

```text
规格/用户选择
      │
      ▼
主 Agent 写 brief（文件白名单、接口、验收命令、禁止范围）
      │
      ▼
实现 Agent：先写测试并观察 RED，再做最小 GREEN 实现
      │
      ▼
测试 Agent：聚焦回归 → 相关回归 → 构建/差异检查
      │
      ▼
安全 Agent：公开内容、路径、凭据、导出/历史边界
      │
      ▼
主 Agent 处理 findings，必要时开独立修复轮
      │
      ▼
文档 Agent：只写已观察事实，留下限制和下一检查点
```

每次交接至少包含：基线提交、任务目标、允许修改文件、禁止触碰的资料/密钥边界、RED 输出、GREEN 输出、最终命令、失败/跳过原因和残余风险。修复轮同样遵循先补回归测试、再修实现、再复跑原命令的顺序。

## 本项目中的实践

- Task 1 先建立公开导出白名单，再用路径、链接、数据库和凭据边界测试它；Task 2～5 逐步补齐模式、Provider、虚构资料和启动脚本。
- 每个任务使用独立的文件清单和提交，保留既有私有/无关未跟踪资产，不把 `.superpowers` 执行包或本机运行数据带入公开副本。
- 审查发现过路径别名、Provider 事件合同、启动器进程归属和悬空 junction 等边界问题；修复先用失败回归证明缺口，再收窄实现，避免用 Demo 专用适配器掩盖正式事件合同。
- Task 6 的文档合同测试把 README 必需章节、相对链接和越界叙述变成可执行约束；它不能代替后续独立公开仓库的全量发布门。

## 协作与产品架构的分界

开发协作可以并行讨论和复核，但产品请求只依赖稳定的 Provider Protocol 和固定 RAG 阶段。这样做的好处是状态、成本、超时和证据边界都集中在一个可测试的工作流里；代价是 v1 没有运行时任务分解和专家路由能力。

运行时多 Agent 是 v2.0 候选方向。若未来实施，需要新的输入/输出合同、Agent 间证据传递规则、预算/超时、失败回退、人工监督和独立评测；不能只把本开发表格复制到产品代码中。

## 可审计性与诚实边界

公开文档保留任务目标、实际代码位置、测试类型、聚合指标和已知限制，但不公开真实资料、私有问题/答案、Provider 原文、Key 或本机路径。私有评测的 C2 结果（14/30、无答案拒答率 60%）按项目负责人确认回滚到 C1；这是决策闭环，不是 Agent 自主发布或自主修改医疗策略。
