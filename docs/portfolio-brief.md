# 作品集导览：医疗知识问答助手

这份导览给招聘方和技术面试官使用。它把项目从“有一个聊天页面”翻译成可追问的能力证据；公开副本只包含虚构资料、脱敏聚合指标和可运行代码。

> **一句话定位：** 我做的不是一个“更敢回答”的医疗聊天机器人，而是一条证据约束的 RAG 工程链：资料有版本，检索有门槛，答案有合同，引用能核对，失败能分类，实验可回滚，公开发布也有边界。

## 招聘方速读卡

| 业务问题 | 我的工程回答 |
| --- | --- |
| 模型可能脱离内部资料自由发挥 | 版本化知识库 + active/approved 过滤 + 证据门 |
| 引用看似存在但无法追溯 | `SourceRef` 保留页码/段落/表格定位，引用集合统一校验 |
| 回答越多，越可能把无答案题答错 | 固定拒答状态、黄金评测集、安全门和可回滚实验 |
| 需要展示 Agent，但不能把 Demo 夸成生产多 Agent | Router、预算、超时、fallback 和零出网预检独立成候选工作流 |

**当前工程基线：** `final-ai-validated-20260904-005`，80 题（64 可回答 + 16 无答案）；正式运行库复评形成回答 57/64，无答案拒答 16/16。上述均为工程代理指标，不是医学准确率。

**最值得追问的三件事：** 为什么 C2 不能只看回答数？为什么 Agent 默认关闭？为什么 staging 和正式运行库必须分开验收？答案分别见[评测与回滚](evaluation.md)、[多 Agent 开发](multi-agent-development.md)和[项目案例](project-case-study.md)。

## 30 秒看懂我做了什么

我把“医护需要快速核对制度和培训资料”的业务问题，收敛成一个本机优先的证据型 RAG PoC：资料有版本和来源定位，检索有门槛，答案必须通过结构与引用校验，证据不足时明确拒答，用户反馈可以进入本地审核闭环。

项目的关键不是让模型更敢回答，而是把“资料是否生效、检索是否命中、答案是否可核对、失败是否可解释”拆成可以独立验证的工程环节。

### 评测集版本口径

仓库里出现的“30 题”和“80 题”不是同一套数据：早期 `corrected V1/V2` 的 30 题属于 Task 9/12/14 历史实验；当前 `2026-standard-manual-v1-golden-v1` 已形成并专业审核冻结 80 题（64 道可回答、16 道无答案），Task18 的当前流程评测固定使用这套 80 题。历史 30 题数字只用于解释回滚和方案演进；80 题冻结不等于临床认证。

## 三个可以现场讲清楚的案例

### 案例一：回答更多，不代表方案更好

在固定的历史 30 题评测口径下，C2 实验从 9/30 增加到 14/30 个正式回答，但无答案题拒答从 100% 降到 60%，低于预先设定的 90% 安全门。因此保留实验报告、回滚到 C1，并把“安全门先于回答率”写成工程决策。

面试时可以继续追问：如果换题集或换资料，为什么不能直接比较两个百分比？答案是必须同时固定题集、资料快照、模型、提示词和指标分母，否则只能说观察到现象，不能说方案普遍变好。

### 案例二：模型不会回答，先查链路而不是先换模型

项目把失败拆成资料不可定位、召回为空、重排未过门、答案结构无效、引用不可核验和 Provider 错误等有限状态。这样可以先定位问题在哪一层，再决定是修资料、修检索、修输出合同还是保持拒答。

### 案例三：把一次性 Demo 变成可持续改进闭环

资料版本、评测集版本、反馈脱敏、管理员审核和晋级条件分别有边界。用户反馈不会直接改 Prompt，也不会自动进入当前黄金集；它先形成可审核的 Bad Case，再由人工决定是否按 `dev/holdout` 分层追加到 `golden-v2` 候选，最后统一复评和冻结。界面证据见[反馈审核与数据飞轮截图](assets/feedback-review.png)。

## 最近一轮真正落地的工程变化

这些变化不是“计划中的想法”，而是已经有代码、私有报告或冻结记录支撑的工程资产；它们与公开 Demo 的默认路径仍然分开：

1. **知识库与切分：** Task15 将 8 册 `2026-standard-manual-v1` 放入隔离 staging，以 Docling `HybridChunker` 为主候选、Legacy 确定性切分为 fallback。首轮为 1,114/1,147 片对照，定位修复版达到 1,114/1,114 可定位，并保留段落/表格定位；第 9 册以后续增量版本加入。
   源项目已将旧索引和旧 staging 运行包先做可恢复归档，再完成最新标准手册正式运行库迁移与本地验收；公开仓库不包含真实资料。
2. **检索逻辑：** 生产默认仍是 Vector → 去重 → Reranker → `0.35` 门；Task14D/E/F 和 Task18 在 staging 里增加 lexical 分支与 balanced RRF（`k=60`），对照显示 Recall@20 `0.607→0.679`，但回答可用率 `72.5%→68.75%`、引用有效率 `77.5%→76.25%`、时延约 `2.00→2.28s`，所以保留实验、不切换默认。
3. **Agent 工作流：** `backend/app/agents` 已实现严格 Router、预算/超时、预接线变体、答案缓冲和 baseline fallback；历史 30 题 A/C 对照暴露过 Router 合同适配问题，修复后仍保持默认关闭。它展示的是 Agent 工程治理和可回退实验，不把开发协作包装成已上线的运行时多 Agent。

当前 80 题黄金集的身份是 `final-ai-validated-20260904-005`（64 可回答 + 16 无答案），Task18/19 的 vector、hybrid 和正式运行库复评均绑定到该题集与知识版本；早期 30 题只用于解释回滚和方法演进。

## 我的贡献如何表述

- **我负责：** 业务范围、优先级、资料边界、验收指标、方案取舍、回滚决定和最终公开范围。
- **AI 协助：** 代码实现、测试编写、实验运行、文档整理和安全扫描。
- **没有声称：** 临床正确率、专家认证、真实用户规模、生产部署、监管合规或医疗决策能力。

这是一项面向医疗业务的 AI 产品验证/工程 PoC，不把它包装成已经上线的临床系统；任何工程指标也不等于医学准确率认证。

## 推荐的 10 分钟阅读路线

1. 运行[无 Key Demo](demo-guide.md)，观察一个有引用答案、一个资料外拒答和一次会话追问；
2. 看[系统架构](architecture.md)，理解资料、检索、答案合同和 SQLite/Qdrant 的边界；
3. 看[工程决策](engineering-decisions.md)和[评测与回滚](evaluation.md)，追问为什么保留基线；
4. 最后看代码中的 `backend/app/ingestion`、`backend/app/rag`、`backend/app/agents`、`backend/app/feedback` 和对应测试。

## 当前状态边界

默认公开 Demo 是单一 RAG 工作流。Docling staging、混合检索和 AgentWorkflow 已有实现与私有评测记录，但默认产品仍不启用这些实验；面向用户的运行时多 Agent、登录 ACL 和多知识域仍属于 v2 候选，不应在面试中混称为默认生产能力。
