# 工程决策

本文只记录当前实现和已经发生的取舍。未实现能力使用“候选”或“v2.0”表述，不把计划当作功能。

## 决策总表

| 决策 | 当前选择 | 主要收益 | 明确代价或边界 |
| --- | --- | --- | --- |
| 默认运行模式 | 显式 Demo，Cloud 由操作者切换 | 无 Key、无网络即可复现完整流程 | Demo 不是开放域模型；Cloud 依赖自备 Key、网络和额度 |
| 关系存储 | SQLite | 零服务依赖，适合本机版本/会话/反馈 | 没有多用户并发、权限和高可用语义；MySQL 留在 v2.0 |
| 向量存储 | Qdrant Local | 本地向量检索与版本过滤可一起演示 | 不承担共享部署和运维；Qdrant Server 留在 v2.0 |
| Provider 边界 | `KnowledgeProvider` / `LanguageModelProvider` Protocol | Demo 与 Cloud 共用 RAG 接口，可测试隔离 | Protocol 只保证调用形状，不保证模型语义质量 |
| 答案策略 | 严格双字段 JSON、完整缓冲、引用门 | 结构不完整或证据不足时整条拒答 | 可用性低于“尽量回答”的策略，需要人工校准 |
| 发布方式 | 白名单导出独立副本 | 把真实资料、运行数据和内部过程与公开副本隔离 | 每次新增公开文件都要更新清单并重新扫描 |
| 开发协作 | 任务级多 Agent + 独立复核 | 规划、实现、测试、安全和文档可交叉检查 | 交接需要报告、基线和明确范围；不是运行时拆分 |

## SQLite 而不是 MySQL

v1.0 的对象是单机工程演示：文档文件名和版本哈希、索引状态、聊天会话、消息、引用和反馈都需要事务边界，但不需要独立数据库服务。SQLite 的 `BEGIN IMMEDIATE`、外键、schema version 和原子版本发布满足本地可重复运行，并让 Demo 的安装路径短。

代价是 SQLite 文件属于本机运行状态，不是权限边界；多个用户、组织 ACL、审计、高并发写入、备份和故障转移都没有实现。若 v2.0 面向共享部署，应先定义租户/角色/审计模型，再评估 MySQL 迁移和数据恢复，而不是仅替换连接字符串。

## Qdrant Local 而不是 Qdrant Server

Qdrant Local 与 SQLite 一样让招聘方在不部署外部服务的情况下检查向量召回、active version 过滤和重建生命周期。检索服务还会在 Provider 返回后再次限制最多 20 条候选，以免不遵守 `limit` 的实现扩大证据面。

Qdrant Local 的向量文件仍是敏感运行数据，不能提交或导出。Server 模式留到 v2.0，届时必须重新验证网络、鉴权、租户隔离、备份和公开部署边界。不能因为接口名称相似，就宣称当前具备 Server 的可用性。

## Demo/Cloud 与模型选择

Demo Provider 使用固定哈希分桶的 1024 维向量、稳定词法重排和严格登记场景匹配，目标是让流程在零成本、零网络环境下可重复，而不是伪装成真实大模型。它会对未知问题返回结构化拒答，对图片 OCR 明确不伪造文本。

Cloud 模式保留现有 Provider 接口：SiliconFlow 承担 `BAAI/bge-m3` Embedding、`BAAI/bge-reranker-v2-m3` Reranker 和批准的 OCR 模型，DeepSeek `deepseek-v4-flash` 负责正式答案和追问改写。前端不接触 Key，后端只使用运行者本机配置。当前公开问答路由不调用 MiniMax 或 TaoToken；私有评测出题和正式问答是不同边界，不能混写。

Cloud 的 Provider HTTP 层有有限的错误处理与资源上限；一次受控云端 smoke 若获授权，额外采用最多 5 个问题、零自动重试的验收政策。该政策不等于把所有正式 Cloud 请求的底层实现描述为没有任何重试，而是明确一次发布验收的成本边界。

## 证据门优先于回答率

检索链固定为最多 20 条召回、去重、最多 6 条 Reranker 结果和 `0.35` 相关性门。生成结果先完整缓冲，再校验 `refused`/`answer` 结构、敏感文本、来源编号和页码/段落位置。任一条引用不合格都会整条拒答，避免“删掉坏引用后展示看似完整的答案”。

这种选择牺牲一部分回答可用性，换取更清晰的失败边界；它仍不能证明语义正确性。Task 9C 的 C2 实验把正式回答从 9/30 提升到 14/30，却把无答案拒答降到 60%，低于 90% 安全门。项目负责人确认回滚到 C1，保留 C2 报告作为可追溯的工程证据，而不是选择更高的单一回答率。

## 为什么不把开发多 Agent 放进产品

开发过程中的主 Agent、实现 Agent、测试 Agent、安全 Agent 和文档 Agent 通过任务边界和复核协作；请求运行时则由一个 FastAPI 应用编排既定的 RAG 阶段。这样做减少运行时成本、状态协调和不可预测失败，同时让 v1 的安全合同更容易审计。

如果未来引入运行时路由，必须先独立设计 Agent 输入/输出合同、预算、超时、证据共享、失败回退和人工监督，并纳入 v2.0 评测，不能仅把开发协作图改名为产品架构。

## 公共发布与许可

公开副本由 `PublicReleaseManifest` 和安全 copier 生成，输出目录必须新建或为空；清单和递归检查会拒绝 `.env`、数据库、日志、私有数据、资料目录、压缩包、符号链接和 Windows reparse point。独立副本还需要后续发布门进行工作树与完整历史检查。

MIT 只覆盖独立公开仓库中实际发布的脱敏代码、虚构资料和文档，不覆盖本地真实资料、私有评测、私人手册、数据库或未导出的开发资产。当前没有创建或推送 GitHub 远程仓库，不能把本地提交误称为公开发布。
